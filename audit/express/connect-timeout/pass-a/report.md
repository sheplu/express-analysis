# Node.js patch audit: connect-timeout

- Verdict: confirmed patching
- Status: complete
- Input: npm package `connect-timeout` (Connect/Express request timeout middleware), audited from a local clone at `$PACKAGE_ROOT`
- Library: connect-timeout 1.9.1, git clone of https://github.com/expressjs/timeout, branch master, commit 7377defb5b7b5a9c3d50fabd42c4dd46ad175d13; installed runtime dependencies at `$PACKAGE_ROOT/node_modules`: depd@1.1.2, ee-first@1.1.1, http-errors@1.6.3, ms@2.0.0, on-finished@2.3.0, on-headers@1.1.0, setprototypeof@1.1.0, statuses@1.5.0, plus nested inherits@2.0.3 under http-errors. No local modifications observed.
- Node.js baseline: main branch, commit d44625a4b80c672215b469906ce583ce7eeeebaf (`$NODEJS_SOURCE`)
- Reproduction runtime: Node.js v24.19.0 (`node repro.js "$PACKAGE_ROOT"`, output in `repro-output.txt` beside this report)
- Scope: production/runtime code only — `$PACKAGE_ROOT/index.js` (sole shipped runtime file per package.json `files`) and the resolved entrypoints/initialization of every installed runtime dependency listed above. Tests, docs, examples, and browser-only files (`depd/lib/browser`, `inherits_browser.js`) out of scope.
- Coverage: full source coverage of the runtime scope; targeted Node.js baseline reads (`lib/internal/http/{server,outgoing,incoming}.js`, `lib/internal/errors.js`, shim `lib/_http_server.js`); upstream corroboration via local git history and the GitHub advisory API; dynamic reproduction run. No unresolved candidates.

## Patching verdict

Patching is demonstrated. Two confirmed findings, both transitive through runtime dependencies that connect-timeout activates:

- 1 core-backed instance override, applied on **every request**: on-headers replaces `res.writeHead` on the live `http.ServerResponse` instance (F-001). connect-timeout activates it per request at `$PACKAGE_ROOT/index.js:66`.
- 1 transient shared-global mutation, applied at **require time**: depd temporarily reassigns `Error.prepareStackTrace` and `Error.stackTraceLimit` process-wide and restores them synchronously (F-002). Three set/restore cycles run unconditionally when `connect-timeout` is required.

No shared core prototype mutations, no core module-loading interception (`require.cache`, `Module._*`, loader hooks: negative searches), no `process.binding`/`internalBinding` use, and no core source rewrites anywhere in the inspected scope. connect-timeout's own writes to the request (`req.timedout`, `req.clearTimeout`) add new library-owned keys and do not override any core member (verified against `$NODEJS_SOURCE/lib/internal/http/incoming.js` and by reproduction). on-finished's node-0.8 `assignSocket` instance patch exists in the shipped dependency code but is unreachable on the audited Node baseline (rejected, C-004).

## Confirmed Node.js patches

### F-001: `res.writeHead` replaced on every live ServerResponse (via on-headers)

- Category: instance/application override of a core-backed instance (shadows `ServerResponse.prototype.writeHead` per response; the shared prototype itself is not mutated)
- Library site(s):
  - Activation: `$PACKAGE_ROOT/index.js:66-68` — `onHeaders(res, function () { clearTimeout(id) })` (https://github.com/expressjs/timeout/blob/7377defb5b7b5a9c3d50fabd42c4dd46ad175d13/index.js#L66)
  - Write: `$PACKAGE_ROOT/node_modules/on-headers/index.js:71` — `res.writeHead = createWriteHead(res.writeHead, listener)` (https://github.com/jshttp/on-headers/blob/v1.1.0/index.js)
  - Replacement implementation: `$PACKAGE_ROOT/node_modules/on-headers/index.js:30-52` (`createWriteHead`), header application helpers at lines 82-180
- Origin: transitive — connect-timeout -> on-headers@1.1.0
- Core baseline: `$NODEJS_SOURCE/lib/internal/http/server.js:423-424` (`ServerResponse.prototype.writeHead = writeHead`; plain data property on the prototype, re-exported through `lib/_http_server.js` and `lib/http.js`), implementation at lines 424-515. Original behavior: validates status code, sets `statusMessage`/`statusCode`, merges headers from the object/array argument into `this[kOutHeaders]` or sends them raw, builds the status line, flushes headers. Commit d44625a4b80c672215b469906ce583ce7eeeebaf.
- Exact mutation: assignment of an own `writeHead` data property on the live response object, shadowing the core prototype method for that instance. The replacement is a closure-wrapped function (named `writeHead`) that keeps a reference to the previous `res.writeHead` (normally the core prototype method, or a previous wrapper if stacked).
- Execution chain: `require('connect-timeout')` -> middleware factory `timeout(time, options)` -> returned middleware runs per request -> `onHeaders(res, listener)` (`index.js:66`) -> `on-headers/index.js:71` write.
- Activation: unconditional on every request that passes through the middleware; production path; no guards, no opt-out.
- Scope and restoration: per-response instance only; never restored for the life of the response; the wrapper delegates to the saved original (`prevWriteHead.apply(this, args)`), so core header serialization still runs. The shared `ServerResponse.prototype.writeHead` is untouched (verified by reproduction).
- Resulting behavior: before the core `writeHead` executes, the wrapper (a) applies the status code via `this.statusCode = statusCode` and applies header arguments through `setHeader`/`removeHeader`+`appendHeader` instead of letting core receive them raw (on-headers/index.js:119-146, 148-180), (b) fires the listener exactly once — for connect-timeout, `clearTimeout(id)`, disarming the timeout as soon as headers are about to be written, (c) re-reads `this.statusCode` afterward so listener changes to the status code are propagated, then calls the original with trimmed arguments. Net effect for connect-timeout: core header-write behavior gains a pre-write hook; headers passed to `writeHead` transit the progressive header API rather than the raw-headers fast path.
- Evidence: static (code above) and dynamic — `repro-output.txt`: before middleware `res` has no own `writeHead`; after one middleware invocation `res` has an own `writeHead` differing from `ServerResponse.prototype.writeHead`, while the prototype is unchanged. Runtime Node v24.19.0.
- Upstream: connect-timeout commit cb5c2ee5aa7700dfaf16945db8fe03c113d5c38d ("use on-headers instead of patching writeHead", May 2014, https://github.com/expressjs/timeout/commit/cb5c2ee5aa7700dfaf16945db8fe03c113d5c38d) shows the maintainers moving an identical in-package `res.writeHead` instance patch into on-headers — the mechanism is the library's intended design, merely centralized. GHSA-76c9-3jph-rj3q / CVE-2025-7339 ("on-headers is vulnerable to http response header manipulation", vulnerable < 1.1.0, patched 1.1.0) corroborates that on-headers' wrapper intercepts and rewrites `writeHead` header handling; the installed 1.1.0 is the patched version (it uses `removeHeader`+`appendHeader` for array headers, on-headers/index.js:158-170).

### F-002: transient process-wide reassignment of `Error.prepareStackTrace` / `Error.stackTraceLimit` (via depd)

- Category: shared global mutation — transient, synchronously saved and restored within the same tick
- Library site(s):
  - `$PACKAGE_ROOT/node_modules/depd/index.js:365-383` (`getStack`): saves both values, sets `Error.prepareStackTrace = prepareObjectStackTrace` and `Error.stackTraceLimit = Math.max(10, limit)`, calls `Error.captureStackTrace`, reads the structured stack, restores both (https://github.com/dougwilson/nodejs-depd/blob/v1.1.2/index.js)
  - `$PACKAGE_ROOT/node_modules/depd/lib/compat/index.js:21-42` (lazy `callSiteToString` initializer): same save/set/capture/restore pattern with `Error.stackTraceLimit = 2`
- Origin: transitive — connect-timeout -> http-errors@1.6.3 -> depd@1.1.2
- Core baseline: `Error.prepareStackTrace` is the documented V8/Node stack-trace customization hook; Node core's own stack preparation defers to a user-assigned value — `$NODEJS_SOURCE/lib/internal/errors.js:145-156` (`prepareStackTraceCallback` invokes `globalThis.Error.prepareStackTrace(error, trace)` when it is a function). On the reproduction runtime (Node 24) a default `Error.prepareStackTrace` function is present before the library loads.
- Exact mutation: data-property writes on the global `Error` constructor: `Error.prepareStackTrace` replaced with depd's `prepareObjectStackTrace` (returns the raw CallSite array) and `Error.stackTraceLimit` replaced with 10 (or 2 in the compat path); both restored to their saved prior values a few statements later.
- Execution chain (require time, unconditional): `require('connect-timeout')` -> `require('http-errors')` (`$PACKAGE_ROOT/index.js:15`) -> (a) `require('depd')` module init reads the lazy compat property `callSiteToString` (`depd/index.js:11` -> `depd/lib/compat/index.js:21-42`), (b) `depd('http-errors')` (`http-errors/index.js:15` -> `depd/index.js:105-110` -> `getStack`), (c) `deprecate.function(exports.ImATeapot, ...)` (`http-errors/index.js:247` -> `wrapfunction`, `depd/index.js:397-405` -> `getStack`). Additional cycles run at any later deprecation logging (`depd/index.js:169-245`), a path connect-timeout's own `createError(503, ...)` call (`index.js:84`) does not trigger.
- Activation: unconditional at module load of connect-timeout; production path; no environment guard prevents the writes (NO_DEPRECATION only suppresses output, not `getStack`).
- Scope and restoration: process-wide while set; restored synchronously in the same synchronous block, so no other JavaScript can observe the window in a single-threaded process (no awaits/yields between set and restore). Caveat: restoration is not wrapped in try/finally — if `Error.captureStackTrace` or stack access threw, the mutated values would persist (not observed; capture of a plain object does not throw on the audited runtime).
- Resulting behavior: during each window, any stack-trace preparation would use depd's formatter and modified frame limit instead of Node's default; in practice only depd's own `Error.captureStackTrace(obj)` runs inside the window, so the observable process behavior before and after is identical.
- Evidence: static (code above) plus dynamic — `repro.js` instruments `Error.prepareStackTrace` with an accessor: 6 writes (3 set/restore cycles, all function values) occur during `require('connect-timeout')`, and both `Error.prepareStackTrace` and `Error.stackTraceLimit` compare identical to their pre-require values afterward (`repro-output.txt`).
- Upstream: this is the canonical use of the documented V8 stack-trace API (https://v8.dev/docs/stack-trace-api), referenced by Node's own comment at `$NODEJS_SOURCE/lib/internal/errors.js:91-93`; `Error.prepareStackTrace`/`Error.stackTraceLimit` are user-assignable by design. Reported as a confirmed (transient) global mutation because the write is reachable, unconditional, and replaces process-wide stack preparation while set; readers weighing only persistent patches may discount it.

## Supporting context

- `req.timedout` / `req.clearTimeout` (C-005/C-006) are the package's documented API surface (README): new keys on the live core `IncomingMessage`, not overrides. Reproduction confirms both are own properties and that core `IncomingMessage.prototype` has neither member.
- `req.emit('timeout', delay)` (C-007) piggybacks on the same event name core uses for `message.setTimeout(msecs, callback)` listener registration (`$NODEJS_SOURCE/lib/internal/http/incoming.js:257-262`): a callback a user registered via `req.setTimeout(..., cb)` would also fire on connect-timeout's artificial emission. This is event-name sharing, not a mutation.
- on-finished reads the deprecated core property `res.finished` (`on-finished/index.js:68-70`) and `msg.complete`/`socket.writable`/`socket.readable` to decide finished-ness — read-only use of core state, partially deprecated API.
- `patchAssignSocket` (C-004) is a genuine instance-override routine shipped inside on-finished@2.3.0 but dead on any Node where `OutgoingMessage` initializes `socket` to `null` (the audited baseline does, `outgoing.js:187`); it targeted node 0.8 where `res.on('socket')` was broken (code comment, on-finished/index.js:191).
- depd's `wrapfunction` uses `eval` at require time (C-015) to build the deprecation wrapper for http-errors' legacy `"I'mateapot"` export — notable for strict-CSP/SES environments, unrelated to core patching.

## Coverage and limitations

- Entry points: `$PACKAGE_ROOT/index.js` is the only shipped runtime file (`package.json` `files`: LICENSE, HISTORY.md, index.js); no install scripts, no conditional exports, no dist/bundled output. Every installed runtime dependency entrypoint was read in full: on-headers@1.1.0, on-finished@2.3.0 (+ ee-first@1.1.1), http-errors@1.6.3 (+ depd@1.1.2 incl. lib/compat, setprototypeof@1.1.0, statuses@1.5.0, nested inherits@2.0.3), ms@2.0.0. - Node.js baseline: targeted reads only at commit d44625a4b80c672215b469906ce583ce7eeeebaf, where the HTTP implementation lives in `lib/internal/http/` with `lib/_http_*.js` as re-export shims. On older Node release lines the same `writeHead`/`assignSocket`/socket-init contracts live in `lib/_http_server.js`/`lib/_http_outgoing.js`; the C-004 unreachability conclusion was verified only against this baseline (and dynamically on v24.19.0) — on node 0.8 that branch would activate and become a second instance override.
- Branches tested: middleware happy path (every-request activation) exercised by reproduction. Not exercised: deprecation logging at runtime (`depd` `log()` — connect-timeout's own `createError(503, ...)` call uses a non-deprecated signature, so this fires only if an application calls deprecated http-errors signatures itself), `respond: false` option (skips only the `req.on('timeout')` listener; the F-001/F-002 writes are unaffected).
- What would change the verdict: nothing found suggests additional patch sites; running on node 0.8 would add the on-finished `assignSocket` instance override (C-004) as a confirmed finding; readers who treat synchronously-restored writes to the documented `Error.prepareStackTrace` hook as supported configuration rather than patching would reduce the confirmed count to F-001 only — the evidence for both is recorded so either policy can be applied.
